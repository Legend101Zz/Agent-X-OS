◆ the one-paragraph version

A CA's biggest headache is that business owners dump them messy financial records — bank-statement PDFs, Excel exports, piles of invoices — and someone has to turn that into clean books by hand (5–10 hours per client, every month). books-prep does the grunt work: it reads the dump, extracts every transaction, categorizes it into a ledger head with a GST treatment and a confidence score, and hands the CA a clean Excel ledger — with anything doubtful pushed to a review queue for the CA to check. It is an assistant that preps the books, never an autopilot that closes them. The market already proved this is the winning shape: even 98%-accurate tools "still require lightweight approval queues for low-confidence items" — which is exactly our verification ladder + human-approval rung.

Why this is the right wedge: one CA is a concentrated buyer with acute, recurring pain and a real budget — and a channel into the 50–200 businesses they serve. It also maps onto the hackathon's Money / Professional-Services / Small-Business categories.

▣ what v0 is — and isn't

✓ in scope (v0)

  • Input: digital-text PDF bank statements + Excel/CSV exports
  • Extract: date · debit · credit · running-balance · narration · reference — deterministically
  • Categorize: MiniMax assigns ledger head + GST treatment + confidence; resolves vendor from narration
  • Verify: rules → judge → CA review queue → reality (CA accepts/corrects)
  • Output: clean Excel ledger, every row source-cited + a queue of flagged items
  • Settle: clean txns → this business's private heap; CA corrections feed the gym

✗ deliberately deferred

  • Scanned / photo statements → routed to human queue in v0 (OCR/vision later)
  • GST reconciliation (GSTR-2B / ITC, GSTR-1/3B, TDS) → a separate gst-recon mandate, spawned from a settled books-prep run
  • Tally / Zoho integration → Excel first; those export adapters come later
  • Signup / Stripe / multi-tenant → separate workstream

Decision: keep books-prep as mandate #1 — it's the clean-data foundation the money mandates stand on (both Dennis & Richa: bad data poisons everything downstream). The suite arc: books-prep → gst-recon → collections (the highest-WTP money mandate; agent drafts, owner approves each send).

Three near-free refinements folded into books-prep

So the foundation actively feeds the next mandates — these are just extra columns the categorizer already emits, no new adapters:

  • +field vendor + GSTIN + state per transaction → feeds gst-recon; guards Dennis's multi-state GST mix-up
  • +flag missing_supporting_doc on expense rows with no bill → is pain #4, as data; the hand-off list to GST/collections
  • +tag receivable / payable → seeds the collections mandate with an ageing-ready dataset

⚙ the harness generalization (the reusable win)

Today the Hermes runner's tools and system prompt are hard-coded to lead-finder. To add any second mandate cleanly, we make them derived from the mandate — its faculties already declare a tool_manifest, so the seam was anticipated; the runner just doesn't use it yet.

before — hard-wired

  • _TOOLS = a fixed list (search_leads, read_url, draft_email…)
  • _system_prompt() = a lead-finder essay
  • _RISK_BY_SYSCALL = a hard-coded dict
  • A 2nd mandate would mean copy-paste + drift

after — mandate-driven

  • _TOOLS = control tools + one per syscall in the mandate's faculties' manifests, schema from the registry
  • prompt = charter.goal + constraints + faculty skill-packs
  • risk + schema come from the contracts registry
  • A 3rd mandate is just config — the goal of the whole OS
The constraint that shapes this: import-linter forbids the kernel (where the runner lives) from importing the syscall package. So the tool-schema registry must live in agentx_contracts — the shared seam both sides may import. Caught before it could break the build mid-way.
Guardrail — lead-finder is regression-locked: a test asserts the generated tools + prompt for lead-finder are byte-identical to today's hard-coded ones. If they match, live behavior is preserved by construction.

The 3 lead-finder couplings in the run loop we unwire

  • modify default sim playbook → a type → playbook resolver (defaults to lead-finder; adds books-prep so the swarm can dry-run it)
  • modify read-result handling → a per-syscall handler registry (keeps lead handlers; adds an ingest_document one)
  • modify sim-native reads → add a synthetic-transactions branch for dry runs

◈ the optional Gemini toggle

You don't have a Gemini key and v0 doesn't need one — PDFs are parsed by deterministic libraries, and MiniMax does the categorization. But we wire a clean toggle for later (and for the hackathon's "≥1 Gemini call in production" rule):

# agentx_contracts/config.py — new settings, default OFF
use_gemini: bool = False
gemini_api_key: SecretStr | None = None
gemini_model_id: str = "gemini-2.5-flash"
gemini_base_url: str = "…/openai/"   # Gemini's OpenAI-compatible endpoint
Why it's nearly free to add: Gemini exposes an OpenAI-compatible API, and Hermes already drives an OpenAI-compatible transport. So the toggle is a one-line transport swap at construction — no runner rewrite. Off by default → MiniMax → nothing changes.

▤ the dashboard contract stays intact

The dashboard talks to a generic surface — none of it changes:

/commands/instantiate /commands/trigger-run /approvals /commands/approve /events (SSE) /runs/{id} /journal

  • Approval cards are already generic — {syscall, args, idempotency_key} — so export_ledger & the review queue render in the existing inbox with zero contract change.
  • Instantiate / trigger are keyed by type_ref; books-prep@0.1.0 flows through once registered in the catalog (mirrors how lead-finder is seeded).
  • The one new input — which documents — rides the trigger payload + a local intake folder. No new endpoint. The studio just gets an additive optional "document path" field; lead-finder's flow is untouched.
